| 提示 | 本地结论 | 建议优先级 |
| --- | --- | --- |
| 系统可能不会面向所有用户显示无边框画面 | 已有部分适配，但缺少旧系统统一启用以及左右挖孔安全区域处理 | 高 |

## 1. 无边框显示兼容性

当前 `app/build.gradle:10`、`:15` 的 compileSdk / targetSdk 均为 36。达到 target 35 的应用在 Android 15 及以上默认无边框显示；更早系统需显式启用。Android 16 上 target 36 也不能依赖退出无边框的主题开关解决。[无边框指南](https://developer.android.com/develop/ui/views/layout/edge-to-edge)、[Android 16 行为变化](https://developer.android.com/about/versions/16/behavior-changes-16)。

现状并非完全未适配：

- `compose/components/HeroSection.kt:53`、`compose/SettingScreen.kt:141` 和 `compose/components/ComposeToolbar.kt:32` 已处理顶部状态栏留白。
- 多数独立 Compose 页面使用 `navigationBarsPadding()`；`MainActivity.kt:92` 处理底部导航栏下方空间。
- `pages/FilterListActivity.kt:109` 为筛选页标题和列表处理系统栏顶部、底部空间。

缺口：

- `ScBaseActivity.kt:17` 没有调用 `enableEdgeToEdge()`，整个项目也未找到统一设置窗口无边框布局的调用。Android 14 及以下与新系统走不同布局路径。
- 筛选页仅处理 `systemBars()` 的 top / bottom，主页面底部导航只取 bottom；未处理左右系统栏以及独立的 `displayCutout()`。横屏挖孔、侧边导航存在遮挡风险，需设备验证。
- Compose 顶部工具栏只处理状态栏，尚无统一的左右安全区域策略。
- 主页面混合 View、Fragment、Compose，需要明确每段区域由谁处理 insets，避免迁移后重复留白；不能直接给整个根布局再统一加四边 padding。

建议：普通页面在基类统一启用兼容无边框；当前 Activity 1.9.3 可使用 `androidx.activity.enableEdgeToEdge`，它从 1.8.0 提供。逐页面保留背景延伸至系统栏，并只给按钮、文字、列表内容添加适当安全区域。`ScreenOffActivity`、`NightGlowActivity` 直接继承平台 Activity，应单独处理全屏黑底、系统栏和锁屏表现。[Activity API](https://developer.android.com/reference/androidx/activity/EdgeToEdge)。

## 2. 已弃用 API / 参数

确定存在的自有代码：

- `ScBaseActivity.kt:31`：`window.statusBarColor = ...`，用 `@Suppress("DEPRECATION")` 隐藏编译警告仍然会保留调用。
- `res/values/styles.xml:15`：普通主题的 `android:statusBarColor`。
- 同文件 `:61`、`:62`：黑屏主题的 `android:statusBarColor`、`android:navigationBarColor`。
- `MainActivity.kt:128` 起仍通过基类设置不同页面的状态栏背景色。

`statusBarColor` 在 Android 15 的相关新目标版本行为下已经失效；导航栏颜色的行为取决于手势或三键导航。现有“内容不画到状态栏后面”的基类注释与新系统强制无边框行为不一致。[Android 15 弃用 API 清单](https://developer.android.com/about/versions/15/behavior-changes-15)。

建议将状态栏区域颜色交给页面背景绘制，继续用 `WindowInsetsControllerCompat` 管理明暗图标。普通主题清理旧颜色设置，黑屏主题结合窗口行为单独验证。仅删除代码不足以完成适配，必须同时完成第 1 项。

Material 1.12.0、Activity 1.9.3、Core 1.13.1 是需要检查的兼容层依赖，但本次未确认它们就是 Console 点名的来源。后续按 Console 给出的类和方法定位，并检查最终 release 包；不能承诺删掉自有调用后提示立即消失，也不应为规避扫描移除库对旧系统的必要兼容逻辑。

## 3. 位图内存

### 应用列表：优先优化全量图标加载

调用链：`FilterListViewModel.readAllApp()` → `AppListState.getInstalledAppList(..., true)` → 每个应用的 `loadIcon()` → `AppInfo.iconDrawable` → ViewModel 保存整个列表 → Glide 展示。

- `states/AppListState.kt:38` 在枚举时就加载每个图标，包括尚未显示的系统应用。
- `model/FilterListViewModel.kt:24`、`:57` 保留全量数据，过滤只改变显示列表，不释放隐藏项的图标。
- `data/AppInfo.kt:11` 用强引用保留 Drawable；其中可能包含位图或多层自适应图标。
- `pages/FilterListActivity.kt:190` 把已经加载好的 Drawable 交给 Glide，无法消除上游已经发生的全量加载与持有。
- `res/layout/item_white_list.xml:20` 图标只显示为 42dp。列表滚动复用 View 并不等于图标内存也仅保留可见项。

建议数据模型只保存包名、名称、选中状态等轻量信息；可见项异步加载图标，按 `42dp × density` 控制目标像素，使用有上限的缓存，并在条目复用时取消旧请求、在页面销毁时释放引用。仅追加 Glide `override()` 不能解决模型强引用问题。Drawable 加载或栅格化仍可能短暂分配原始资源，应同时测量峰值。

量级示例（非本应用实测）：300 张 192×192 ARGB_8888 图像的像素数据约 42.2 MiB；实际取决于可见安装应用数量、图标层数和系统加载实现。

### 应用介绍页：解码方式存在崩溃风险

`compose/AppInfoScreen.kt:46` 对 `R.mipmap.ic_launcher` 调用 `BitmapFactory.decodeResource(...).asImageBitmap()`。但 Android 26+ 对应资源是 `res/mipmap-anydpi-v26/ic_launcher.xml` 中的 adaptive-icon，并非 PNG。

BitmapFactory 无法解码这种 Drawable XML；返回 null 后直接转换会导致崩溃。此处是代码与资源类型不匹配的静态结论，本次未在设备上复现。页面仍在 Manifest 注册，且 `AboutThisPageActivity.kt:19` 保留跳转代码。

建议使用兼容 Drawable 的加载方式，再按 96dp 的实际像素尺寸绘制，并处理失败回退；可与设置页的应用图标绘制逻辑合并。[BitmapFactory 源码及返回值约定](https://android.googlesource.com/platform/frameworks/base/+/3e7d977/graphics/java/android/graphics/BitmapFactory.java)。

### 已有资源并非都需要转换

`compose/SettingScreen.kt:304` 已用 `remember` 保存按 72dp 实际像素绘制的图标，不会每次普通重组都分配新图；密度变化后的缓存键可进一步完善。资源目录内 PNG 共 15 张，均为启动图标，最大为 432×432；未发现大尺寸照片类资源。

把 PNG 改成 WebP 通常主要降低文件体积，不能单靠压缩格式保证解码后的像素内存下降。带透明度的应用图标不宜统一改成 RGB_565；优先控制尺寸、数量和缓存生命周期。[位图内存优化指南](https://developer.android.com/topic/performance/vitals/bitmap-memory-usage)。

Console 这一提示是否对应真实高内存指标仍需查看详情；没有采样数据，不能将其认定为已发生 OOM 或内存泄漏。

## 4. R8

当前配置已符合基础优化要求：

- `app/build.gradle:51`：`minifyEnabled true`。
- `app/build.gradle:52`：`shrinkResources true`。
- `app/build.gradle:54`：使用 `proguard-android-optimize.txt`。
- `gradle.properties` 没有 `android.enableR8.fullMode=false`；AGP 为 8.11.1。
- 两个模块的自有 ProGuard 文件只有注释，没有禁用优化的全局规则。
- `uicomponent` 是库模块，其 `minifyEnabled false` 不会阻止最终应用 release 的 R8 处理库代码。
- `.github/workflows/release.yml` 构建的是 `assembleRelease bundleRelease`。

因此不需要再“打开一次 R8”。AGP 8.11.1 已能做代码和资源优化；8.12+ 的代码与资源联合优化管线是进一步选项，不是这条建议的基础前提。[官方 R8 配置指南](https://developer.android.com/topic/performance/app-optimization/enable-app-optimization)。

核查时发现旧产物：`app/release/app-release.aab` 实际为 `30300 / 3.0.3`，原 `app/build/outputs/bundle/release/app-release.aab` 为 `41000 / 4.1.0`；两者均内嵌 R8 mapping。原 release APK 的元数据又属于 `40000 / 4.0.0`。这些文件不能证明线上 42000 包的状态。

后续应核对 Play Console 的版本、轨道和实际上传 AAB，检查包内 `BUNDLE-METADATA/com.android.tools.build.obfuscation/proguard.map`、构建日志与最终合并规则。确认提示是泛化建议还是针对具体产物；“平台误报”和“上传错包”目前都只是待排查可能，不能作为结论。

### 本次构建验证结果

- 当前代码执行 `./gradlew :app:bundleRelease --console=plain` 成功，耗时 4 分 9 秒；日志确认执行 `:app:minifyReleaseWithR8`。
- `lintVitalRelease` 通过，报告为 `No issues found.`。这是发布关键静态检查，不等同于完整 UI 或内存测试。
- 新生成 `app/build/outputs/bundle/release/app-release.aab` 的 Manifest 为 `42000 / 4.2.0`，包内 mapping 标记 `compiler: R8`、`compiler_version: 8.11.18`。
- 最终 `app/build/outputs/mapping/release/configuration.txt` 未包含 `-dontoptimize`、`-dontshrink`、`-dontobfuscate` 全局禁用规则；生成了 mapping、usage、seeds、resources 报告。
- 本次 AAB SHA-256：`ae069653ddec2b49d6bb0ec106a46bd586d650496113ecff7c7ef781d03749a4`。

由此确认：当前源码构建的 4.2.0 release 确实使用 R8。该包未上传，不能据此证明线上 AAB 与本次产物一致。构建另有 Gradle 未来版本兼容性和原生库符号剥离提示，不属于本次四项结论；本次未运行设备回归或内存采样。
